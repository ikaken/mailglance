# mailglance 設計メモ（Gmail 専用 Windows アプリ）

## 背景と課題

- Gmail を Chrome の別プロファイルで開いている。
- 2段階認証のメールのリンクを開くと、ログイン作業中のウィンドウではなく、Gmail を開いているプロファイルのウィンドウで開いてしまい、認証がうまくいかないことがある。
- 原因：Gmail も Chrome の中にあるため、メールを読んだ時点で Gmail のウィンドウが「最後にアクティブな Chrome ウィンドウ」になってしまう。

## 目的

- Gmail を Chrome の外、専用の Windows アプリで開く。
- アプリ内のリンクをクリックしたら、最後にアクティブだった Chrome のウィンドウ（直前まで作業していたウィンドウ）で開く。

## 方針

- ハイブリッド方式：読む機能は Gmail API で取得して独自の画面に表示する。書く機能（返信・全員に返信・転送）は API で下書きを作り、WebView2 の Gmail の画面で開いて編集・送信する。新規作成と振り分け設定は、WebView2 で Gmail の画面を開く。
- 理由：
  - ローカルキャッシュで起動直後に一覧と本文を即表示し、裏で最新に更新できる。
  - 将来、メールをローカルに保存する機能に広げられる。
  - 編集・送信・振り分け設定は Gmail の画面に任せるので、開発の手間を抑えられる。

## 優先順位

1. メールのリンクをクリックしたら、最後にアクティブだった Chrome のウィンドウで開く。
2. レスポンス：起動したらメール一覧がすぐ出る。件名をクリックしたら本文がすぐ出る。
3. 前回のデータをキャッシュして先に表示し、裏で最新に更新する。

## 主な機能

### 1. リンクの処理

- 本文の HTML は WebView2 で表示し、リンクのクリックを横取りする。
- URL をプロファイル指定なしで Chrome（または既定のブラウザ）に渡す。
- Chrome は最後にアクティブだったウィンドウで開く（`chrome.exe <URL>` は最後に使ったプロファイルのウィンドウで開く）。
- Chrome が見つからない場合は既定のブラウザで開く。その場合「最後にアクティブなウィンドウで開く」かどうかはブラウザ次第。

### 本文 HTML の安全な表示

- 本文中のスクリプトは実行しない（CSP で禁止し、サンドボックスで表示する）。
- 外部画像（トラッキング画像を含む）は既定でブロックし、「画像を表示」ボタンで読み込む。
- フォーム送信やページ遷移は許可せず、リンクはすべて上記の方法で外部ブラウザに渡す。

### 2. 複数アカウント

- アカウントごとに OAuth で認証し、トークンとキャッシュを分けて保存する。
- Gmail 画面用の WebView2 も、アカウントごとにユーザーデータフォルダを分けてログイン状態を保つ。

### 3. 画面構成（Gmail のウェブ版に合わせる）

- 上部に検索欄、右上に閲覧ウィンドウの切り替えと設定。
- 左端にアカウントのアイコンを縦に並べ、クリックで切り替える。各アイコンに未読数のバッジ。
- その右にラベルの列：作成ボタン、お気に入りのラベル、未読があるラベル、送信済みなど。幅はドラッグで変えられる（保存する）。折りたたみもできる。
- 右側にメール一覧と本文。閲覧ウィンドウは「なし・右・下」を切り替える。一覧と閲覧ウィンドウの境界はドラッグで動かせる。
- メール一覧は 1 行形式で、下へスクロールすると続きを読み込む（ページ送りはしない）。
- 本文のヘッダーに、アーカイブ（アーカイブ済み・ゴミ箱では「受信トレイに移動」）、削除、未読／既読、スター、全員に返信、Gmail で開くを置く。本文の下に返信・全員に返信・転送。

### 4. 検索

- Gmail と同じ検索の書き方を API にそのまま渡し、結果をアプリ内に表示する。

### 5. Gmail 画面との連携（WebView2）

- 返信・全員に返信・転送：Gmail API で下書きを作り、その下書きを Gmail の画面で開く。
  - 返信は元のスレッドにつなぎ（In-Reply-To・References・threadId）、宛先は Gmail と同じ規則で決める（Reply-To を優先、自分のメールへの返信は元の宛先、自分と重複を除く）。引用を本文に入れる。
  - 転送は新しいスレッドで、元の本文を引用し、添付ファイルとインライン画像を付ける。大きなメールを送れるメディア アップロード方式（`uploadType=media`）で下書きを作る。合計 25 MB を超えるときはエラーにする。
  - 日本語の件名・表示名・ファイル名は RFC 2047 でエンコードする（そのまま書くと Gmail が文字化けさせる）。ヘッダーに改行が混ざらないよう 1 行にまとめる。
  - 開いている Gmail のページは API で作った下書きを知らない。URL の `#` 以降だけを変えても再読み込みされず、空の新規作成画面が開くため、URL にクエリを付けて毎回読み込み直させる。
  - 送らずに閉じた下書きは Gmail の下書きに残る（自動では消さない）。
- 新規作成：Gmail の画面を開いて行う。
- 振り分け設定ボタンで、WebView2 に Gmail のフィルタ設定画面を開く。
- 将来：「このメールから振り分けを作る」ボタンを API で実装する案。
- Gmail ウィンドウは、新しく作るときに Google のサインイン画面から始める（ログイン済みならそのまま Gmail に進む）。Gmail の案内ページ（未ログイン時に出る）の「ログイン」リンクは別ウィンドウで開く指定で、ウィンドウの中ではログインできないため。
- WebView2 のウィンドウは、必ず非同期のコマンドの中で作る。Windows では、同期のコマンド（メインスレッドで動く）の中で作ると、ページが `about:blank` のまま固まり、× でも閉じられなくなる。

## 配布と認証

- 最初は自分専用。将来は GitHub で公開する。
- 利用者は各自の Google Cloud でクライアント ID とシークレットを作り、アプリの設定画面に入力する。そのあと各アカウントで OAuth 認証する。
- 理由：Gmail の読み取り権限は制限付きスコープのため、共通のクライアント ID で配布すると Google の審査とセキュリティ評価が必要になる。
- 初回公開は IT に詳しい人向けと割り切り、スクリーンショット付きの設定ガイドを用意する。
- クライアント ID とシークレットはリポジトリに含めない。
- OAuth はデスクトップアプリ向けの方式で行う：外部ブラウザでログインし、loopback（`http://127.0.0.1:<空きポート>`）で認可コードを受け取り、PKCE を使う。デスクトップアプリのシークレットは事実上秘密にできないため、PKCE で保護する。
- スコープは `gmail.modify`（既読・ラベル変更に必要。読み取りも含む）。`gmail.readonly` では既読化やラベル操作ができない。どちらも制限付きスコープ。
- 同意画面のアプリ名に「Gmail」「Google」を含めない（Google のブランド規定に触れるおそれ）。アプリ名は「mailglance」とする。
- 利用者が増えたら、Google の審査を受けて共通のクライアント ID で配布することを検討する。

## 配布と自動更新

- 配布は NSIS のインストーラー。ユーザー単位（管理者権限なし）にして、設定・キャッシュが入る `%APPDATA%` と相性を合わせる。MSI は、会社での一括配布が必要になったら足す。Inno Setup と Velopack は、画面の作り込みや差分更新が必要になるまで採用しない（Tauri のビルドに組み込まれず、手順が増えるため）。
- 自動更新は Tauri の updater プラグイン。起動の約 15 秒後と 1 日に 1 回、GitHub Releases の `latest.json` を確認する。新しい版があれば、右下に案内を出し、本人が「今すぐ更新」を押したときだけ、ダウンロードして、署名を検証して、インストールして、再起動する（バックグラウンドでの自動適用はしない）。Gmail の API は使わないので、クオータには影響しない。
- 更新用の署名キー（minisign 形式）は Tauri のもの。公開鍵は `tauri.conf.json`、秘密鍵とパスワードはリポジトリの外に置く。秘密鍵をなくすと、インストール済みのアプリを更新できなくなる。
- 配信先は GitHub Releases（リポジトリは公開済み）。非公開のままでは、updater が認証なしで取得できないため使えない。
- 確認済み：ローカルのサーバーに置いた 0.1.1 を、インストール済みの 0.1.0 が見つけ、ダウンロードして、署名を検証し、インストールして、再起動し、設定とアカウントを引き継いだ。
- リリースの自動化：`v*.*.*` のタグを push すると、GitHub Actions（Windows）が、バージョンの一致を確かめ、型チェックと Rust のテストを通し、インストーラーを作って署名し、**下書き**のリリースに `latest.json` と一緒に添付する。タグが main にないときは失敗する。下書きを人が確認して公開した時点で、利用者に更新が届く（公開前に止められる関門にする）。署名キーは、そのステップだけに渡す。使う Actions は 3 つだけで、コミットのハッシュで固定する。PR では、別のワークフローが、バージョンの一致・型チェック・Rust のテストを実行する。
- 未実施：実際のリリース（ワークフローの動作確認）、`latest.json` のダウンロード URL の形式の確認（tauri-action v1 で、ブラウザ用の URL から GitHub の URL に変わった）、Windows のコード署名（Authenticode）、署名が合わないファイルを拒否する動作の確認。バージョン番号は 5 か所（`package.json`、`package-lock.json`、`tauri.conf.json`、`Cargo.toml`、`Cargo.lock`）にあるため、`scripts/set-version.mjs` で揃え、`scripts/check-version.mjs` で確かめる。

## リスク

- WebView2 内での Google ログイン：Google は埋め込みブラウザからのログインを「安全でないブラウザ」として拒否することがある。
  - 確認済み：WebView2 の Gmail ウィンドウで Google にログインでき、返信の下書きも開けた（拒否されなかった）。
  - 将来 Google 側の扱いが変わって拒否されたときの代替：返信・作成・振り分け設定は外部ブラウザで Gmail を開く（Gmail を開いたウィンドウが「最後にアクティブ」になる点に注意）。
- OAuth 認証は外部ブラウザで行うので、この制限は受けない。
- 下書きを API で作るため、送らずに閉じた下書きが Gmail に残る。

## 将来拡張

### プッシュ通知による同期

- 初期版は数十秒ごとの定期更新で、スマホなど他の端末での変更（既読・ラベルなど）を反映する。
- 将来、Gmail のプッシュ通知（Google Cloud Pub/Sub）でほぼリアルタイムに反映する。
- 仕組み：
  1. Pub/Sub のトピックを作り、Gmail がそこに書き込めるよう権限を与える。
  2. Gmail API の watch で、アカウントの変化をトピックに通知するよう登録する。
  3. アプリは pull 方式でトピックを待ち受ける（自前のサーバーは不要）。
  4. 通知を受けたら、前回からの変更を API で取得し、画面とキャッシュを更新する。
- 注意点：watch の登録は 7 日で切れるため、毎日程度で登録し直す。Google Cloud の設定が増える。

## 技術候補

- Rust + Tauri（軽さ・起動の速さ・省メモリを重視）
- Rust 側：Gmail API 通信、OAuth、ローカルキャッシュ、裏での更新
- 画面：Svelte（軽さ優先。Tauri が Windows では WebView2 で表示）
- メール本文の HTML 表示と Gmail 画面（返信・振り分け設定）も WebView2 で扱う

2. ローカルキャッシュ（SQLite）と、60 秒ごとの裏での更新。

## 決定事項

- Svelte の構成：素の Svelte 5 + Vite（Tauri v2 の公式テンプレート）。ルーティングが不要なため SvelteKit は使わない。
- キャッシュ：SQLite（rusqlite、アカウントごとに 1 ファイル）。更新の間隔は 60 秒。
- 設定（クライアント ID・シークレット、アカウント一覧）はアプリのデータフォルダの JSON に保存する。リフレッシュトークンは Windows の資格情報マネージャー（keyring）に保存する。
- Chrome 以外が既定のブラウザの環境：Chrome が見つからなければ既定のブラウザで開く。
- 返信・全員に返信・転送は、Gmail API で下書きを作って Gmail の画面で開く（Gmail の画面の返信ボタンを自動で押す方式や、宛先と件名だけを渡す作成画面の URL は採用しない。前者は画面構造の変更に弱く、後者はスレッドにつながらない）。下書きの作成は `gmail.modify` スコープで足りる。
- 一覧はページ送りではなく連続スクロールにする。続きの読み込みはスクロールしたときだけで、先読みしない。

## API の利用上限

- 2026年5月1日以降に作った Google Cloud プロジェクトは、1 分あたり 1 ユーザー 6,000 単位。messages.get は 20 単位（本文を含む format=full は 60 単位）、messages.list は 5、labels.get は 1、history.list は 2。
- アプリ側で直近 1 分の使用量を数え、5,000 単位を超えそうなら待ってから呼ぶ（エラーにしない）。
- 一覧は 50 件ずつ読む。下へスクロールしたときだけ続きを読み、キャッシュ済みのメールは読み直さない。1 回の続きの読み込みは最大で約 1,000 単位（一覧 5 + 未キャッシュのメール 50 件 × 20）。
- 60 秒ごとの自動更新は、最新の 50 件の一覧取得（5 単位）と新着分だけにする。読み込み済みの古い分は、変更履歴（history）の結果をキャッシュから読み直して反映する（API は呼ばない）。
- 返信・全員に返信は約 30 単位（ヘッダー取得 20 + 下書き作成 10。本文が未キャッシュなら + 60）。転送は約 70 単位（元のメール全体 60 + 下書き 10）と、添付 1 つにつき 20 単位。
- 失敗した続きの読み込みは、自動では再試行しない（再試行の繰り返しを避ける）。
- 本文の先読みはしない（読む順番は予測できず、1 通 60 単位と高いため）。本文はクリックしたときに読み、キャッシュに残す。
- 検索は Gmail のサーバー側で行う（本文を含む全件が対象）。ローカルに本文は不要。
- ラベルの未読数は、他の端末で変更があったとき（history に記録があるとき）だけ取り直す。
- 参考：https://developers.google.com/workspace/gmail/api/reference/quota
